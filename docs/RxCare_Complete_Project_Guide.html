الفصل الأول — مقدمة المشروع

1.1 ما هو نظام RxCare؟

RxCare هو نظام متكامل لإدارة الصيدليات (Pharmacy Management System) صُمّم وبُرمج بلغة Python 3 مع قاعدة بيانات علائقية SQLite. يضم المشروع نسختين تشغيليتين متكاملتين تتشاركان نفس منطق الأعمال (Business Logic):

  1. النسخة المكتبية (Desktop Edition): تعمل محلياً باستخدام مكتبة الواجهات الرسومية القياسية Tkinter / ttk عبر نقطة الدخول main.py وقاعدة بيانات data/pharmacy.db.
  2. نسخة الويب ثنائية اللغة (Bilingual Web Edition): تعمل عبر المتصفح باستخدام إطار العمل Streamlit عبر نقطة الدخول web_app/app.py وقاعدة بيانات معزولة data/pharmacy_web.db مع دعم كامل للغة العربية (RTL) والإنجليزية (LTR).

1.2 المشكلة التي يعالجها النظام

تواجه الصيدليات الصغيرة والمتوسطة عند الاعتماد على الدفاتر الورقية أو جداول البيانات التقليدية (Excel) عدة مخاطر تشغيلية وصحية:

  • بيع أدوية منتهية الصلاحية (Expired Medicines): الخطأ البشري في قراءة تاريخ الصلاحية يهدد سلامة المرضى ويعرض الصيدلية للمساءلة القانونية.
  • نقص المخزون المفاجئ (Stock-outs): عدم وجود تنبيه مبكر عند انخفاض الرصيد عن حد إعادة الطلب (reorder_level).
  • تضارب الحسابات والأرباح: صعوبة تتبع سعر التكلفة (cost_price) مقارنة بسعر البيع (unit_price) وحساب الخصومات والضرائب وصافي الربح اليومي بدقة.
  • انقطاع الترابط بين المشتريات والمبيعات: صعوبة معرفة أي مورد (Supplier) يزود الصيدلية بكل تشغيلة (Batch).

1.3 لماذا تحتاج إدارة الصيدلية إلى برمجيات متخصصة؟

الصيدلية ليست متجراً عادياً؛ فهي تتعامل مع تشغيلات دوائية (Batches) لكل منها تاريخ صلاحية مختلف (expiry_date) وقيود بيع صارمة. البرمجية المتخصصة تفرض قواعد السلامة آلياً (مثل منع بيع الدواء المنتهي في نقطة البيع على مستوى الخدمة وقاعدة البيانات)، وتضمن الذرية في المعاملات (Atomic Transactions) بحيث لا ينقص المخزون دون إصدار فاتورة، ولا تُصدر فاتورة دون خصم المخزون.

1.4 أهداف المشروع

  1. أتمتة دورة حياة الدواء من التوريد حتى البيع للعميل.
  2. منع صرف أو بيع أي تشغيلة دوائية منتهية الصلاحية برمجياً.
  3. توفير نقطة بيع سريعة (POS) تحسب الإجمالي والخصم والضريبة وصافي الربح تلقائياً.
  4. إنشاء سجل تدقيق (stock_adjustments) يوثّق كل زيادة أو نقصان في المخزون.
  5. تقديم لوحة تحكم وتقارير مالية ورسوم بيانية لدعم اتخاذ القرار.
  6. دعم المستخدم العربي والأجنبي بواجهة ثنائية اللغة (عربي RTL / إنجليزي LTR).

1.5 نطاق المشروع وحدوده (Scope & Limitations)

  • ضمن النطاق: إدارة الأدوية والتشغيلات، إدارة الموردين، نقطة البيع والفواتير، تنبيهات الصلاحية وانخفاض المخزون، شطب المخزون المنتهي، التقارير اليومية وتصدير CSV، واجهة مكتبية وواجهة ويب سحابية.
  • خارج النطاق حالياً (القيود): لا يوجد نظام تسجيل دخول وصلاحيات مستخدمين (Authentication/RBAC) في النسخة الحالية، وقاعدة البيانات الافتراضية على الاستضافة السحابية المجانية هي ملف SQLite محلي مؤقت.

1.6 المتطلبات الوظيفية وغير الوظيفية

المتطلبات الوظيفية (Functional Requirements):

  • عمليات CRUD الكاملة للأدوية والموردين.
  • البحث والتصفية حسب الاسم، الاسم العلمي، رقم التشغيلة، التصنيف، أو حالة التوفر.
  • التحقق في POS من الصلاحية وتوفر الكمية وحساب المجموع والخصم والضريبة والربح.
  • تقارير زمنية وتصدير CSV.

المتطلبات غير الوظيفية (Non-Functional Requirements):

  • الموثوقية وسلامة البيانات (Data Integrity): استخدام معاملات SQLite الذرية والقيود المرجعية (FOREIGN KEY و CHECK).
  • الأداء وتعدد الخيوط (Thread Safety): استخدام قفل threading.RLock ووضع WAL في نسخة الويب.
  • قابلية الصيانة (Maintainability): فصل الطبقات (UI / Services / Models / Database).
  • سهولة الوصول (Accessibility & Localization): تصميم داكن واضح التباين مع دعم RTL كامل للغة العربية.

3.2 فصل الطبقات (Layered Architecture)

اعتمد المشروع نمط العمارة الطبقية (Layered Architecture) المكون من 4 طبقات:

  1. طبقة العرض (Presentation Layer): مسؤولة فقط عن عرض البيانات واستقبال المدخلات (pharmacy/ui/ لسطح المكتب، و web_app/pages_ui/ للويب).
  2. طبقة الخدمات (Service Layer): تحتوي على جميع القواعد التجارية والحسابات والتحقق (SupplierService, InventoryService, SalesService, ReportService, WebAnalyticsService).
  3. طبقة النماذج (Domain Models Layer): تمثل هياكل البيانات النظيفة (@dataclass في pharmacy/models/entities.py).
  4. طبقة البيانات (Database Layer): تتولى الاتصال بـ SQLite وتنفيذ الاستعلامات والمعاملات (DatabaseManager و WebSQLiteDatabaseManager).

3.3 كيف تتعايش النسخة المكتبية ونسخة الويب معاً؟

+-----------------------------------+      +----------------------------------------+
|   Desktop UI (Tkinter / main.py)  |      |   Web UI (Streamlit / web_app/app.py)  |
+-----------------+-----------------+      +-------------------+--------------------+
                  |                                            |
                  |                                            v
                  |                        +----------------------------------------+
                  |                        | Web Layer: i18n, WebSessionController, |
                  |                        |            WebAnalyticsService         |
                  |                        +-------------------+--------------------+
                  |                                            |
                  +--------------------+-----------------------+
                                       |
                                       v
                  +--------------------------------------------+
                  |   Shared Business Services (pharmacy/)     |
                  | Supplier | Inventory | Sales | Report      |
                  +--------------------+-----------------------+
                                       |
               +-----------------------+-----------------------+
               |                                               |
               v                                               v
+------------------------------+             +----------------------------------+
| Desktop DatabaseManager      |             | WebSQLiteDatabaseManager         |
| check_same_thread=True       |             | check_same_thread=False + RLock  |
| -> data/pharmacy.db          |             | -> data/pharmacy_web.db          |
+------------------------------+             +----------------------------------+

لماذا أنشأنا محولاً خاصاً للويب (WebSQLiteDatabaseManager) بدلاً من تعديل DatabaseManager الأصلي؟

  1. النسخة المكتبية تستخدم check_same_thread=True لأن Tkinter يعمل في خيط رئيسي واحد.
  2. أما Streamlit فيشغل إعادة التنفيذ (Rerun) عبر عدة خيوط عمل (Worker Threads). استخدام اتصال SQLite مقيد بخيط واحد يسبب خطأ sqlite3.ProgrammingError.
  3. لذلك ورث WebSQLiteDatabaseManager نفس مخطط الجداول ونفس منطق SAVEPOINT من DatabaseManager دون تعديل الملف الأصلي، مع إضافة check_same_thread=False وقفل threading.RLock() وعزل مسار التخزين في data/pharmacy_web.db.

  1. المتغيرات وأنواع البيانات (Variables & Data Types): استخدام int للكميات، float للأسعار والنسب، str للتواريخ والأسماء، وdict/list لتخزين السلة والسجلات.

7.1 الاتصال بقاعدة البيانات والمعاملة الذرية (pharmacy/database/db_manager.py)

@contextmanager
def transaction(self) -> Iterator[sqlite3.Connection]:
    conn = self.connection
    is_outer = self._tx_depth == 0
    savepoint_name = f"sp_{self._tx_depth}"

    if is_outer:
        conn.execute("BEGIN IMMEDIATE;")
    else:
        conn.execute(f"SAVEPOINT {savepoint_name};")

    self._tx_depth += 1
    try:
        yield conn
    except Exception:
        if is_outer:
            if conn.in_transaction:
                conn.execute("ROLLBACK;")
        else:
            conn.execute(f"ROLLBACK TO SAVEPOINT {savepoint_name};")
            conn.execute(f"RELEASE SAVEPOINT {savepoint_name};")
        raise
    else:
        if is_outer:
            if conn.in_transaction:
                conn.execute("COMMIT;")
        else:
            conn.execute(f"RELEASE SAVEPOINT {savepoint_name};")
    finally:
        self._tx_depth -= 1

الشرح للمبتدئين:

  • عند بدء العملية (is_outer = True) يفتح الكود معاملة حصرية BEGIN IMMEDIATE تمنع أي كتابة متضاربة.
  • إذا استُدعيت معاملة داخل معاملة أخرى (_tx_depth > 0) يُنشئ نقطة حفظ SAVEPOINT.
  • داخل try يتم تمرير الاتصال yield conn لتنفيذ عمليات SQL.
  • إذا حدث أي استثناء في منتصف العمل، ينتقل التنفيذ إلى except فيتم التراجع الكامل (ROLLBACK) ولا يُحفظ أي تعديل جزئي! أما عند النجاح فينفذ COMMIT.

def is_expired(expiry_iso: str, reference_date: date | None = None) -> bool:

7.4 حساب صافي الربح (web_app/core/web_services.py)

في WebAnalyticsService.get_profit_summary(...) وcalculate_cart_profit(...):

  • إيراد البنود = مجموع (سعر البيع × الكمية).
  • تكلفة البضاعة المباعة (COGS) = مجموع (cost_price × الكمية).
  • إجمالي الربح (Gross Profit) = إيراد البنود − التكلفة.
  • صافي الربح (Net Profit) = إجمالي الربح − قيمة الخصم الممنوح على الفاتورة.

ثانياً: أسئلة لغة بايثون والبرمجة كائنية التوجه (OOP)

  1. ما الفرق بين الفئة (Class) والكائن (Object) مع مثال من المشروع؟ الفئة هي القالب مثل class Medicine أو class SalesService، والكائن هو نسخة حية منه في الذاكرة مثل sales_service = SalesService(db).
  2. ما فائدة @dataclass في entities.py؟ تُنشئ تلقائياً __init__ و__repr__ لتمثيل الكيانات مثل Supplier وCartItem بكود نظيف ومختصر.
  3. ما دور الدالة البانية __init__؟ تهيئ الكائن عند إنشائه؛ مثلاً DatabaseManager.__init__ يفتح الاتصال بقاعدة البيانات ويفعّل المفاتيح الأجنبية وينشئ الجداول.
  4. أين استخدمت الوراثة (Inheritance) في المشروع؟ WebSQLiteDatabaseManager يرث من DatabaseManager ليعيد استخدام بناء الجداول والبيانات الأولية مع إضافة أمان الخيوط للويب.
  5. ما هو التغليف (Encapsulation) وكيف طُبق؟ إخفاء التفاصيل الداخلية مثل self._conn وself._lock داخل DatabaseManager والسماح بالتعامل معها عبر واجهات منظمة مثل transaction().
  6. ما هو Context Manager (with) وأين استخدمته؟ آلية تضمن فتح المورد وإغلاقه تلقائياً؛ استخدمنا @contextmanager def transaction() لضمان COMMIT أو ROLLBACK تلقائياً.
  7. ما الفرق بين ValidationError و BusinessRuleError؟ الأول لأخطاء صيغة المدخلات (مثل تاريخ خاطئ أو حقل فارغ)، والثاني لانتهاك قواعد الصيدلة (مثل بيع دواء منتهي أو حذف مورد مرتبط بأدوية).
  8. ما فائدة Protocol في db_adapter.py؟ يحدد عقداً برمجياً (DatabaseBackend) يصف الدوال المطلوبة من أي قاعدة بيانات دون ربط الكود بنوع قاعدة بيانات واحد.
  9. كيف تعاملت مع معالجة الأخطاء (try / except)؟ نلتقط الأخطاء في طبقة الواجهة ونترجمها للمستخدم عبر localize_error() مع منع انهيار البرنامج.
  10. لماذا استخدمنا Type Hints (-> float, list[Medicine])؟ لزيادة وضوح الكود وتسهيل اكتشاف الأخطاء قبل التشغيل.

ثالثاً: أسئلة قواعد البيانات و SQL

  1. لماذا اخترت SQLite بدلاً من MySQL أو PostgreSQL؟ لأنه قاعدة بيانات مدمجة بلا خادم خارجي، مثالية للتطبيقات المكتبية والنماذج السحابية السريعة وتدعم معاملات ACID.
  2. ما الفرق بين المفتاح الأساسي (Primary Key) والمفتاح الأجنبي (Foreign Key)؟ الأساسي يميز كل صف داخل جدوله (medicines.id)، والأجنبي يربط صفاً بجدول آخر (medicines.supplier_id -> suppliers.id).
  3. ما فائدة PRAGMA foreign_keys = ON; في SQLite؟ افتراضياً لا تفرض SQLite قيود المفتاح الأجنبي ما لم يتم تفعيل هذا الأمر عند كل اتصال.
  4. لماذا استخدمنا ON DELETE RESTRICT بين المورد والأدوية؟ لمنع حذف مورد ما زالت له أدوية مسجلة في المخزون حفاظاً على سلامة البيانات.
  5. لماذا حفظنا medicine_name وbatch_number داخل sale_items رغم وجود medicine_id؟ كـ Snapshot حتى تبقى الفواتير التاريخية دقيقة إذا تغير اسم الدواء أو سعره لاحقاً.
  6. ما هي المعاملة (Database Transaction) ولماذا هي ضرورية في نقطة البيع؟ مجموعة أوامر SQL تُنفذ كوحدة واحدة لا تتجزأ (ACID). في البيع، إذا فشل خصم الصنف الثاني في السلة تتراجع قاعدة البيانات عن الفاتورة وعن خصم الصنف الأول بالكامل.
  7. لماذا استخدمنا BEGIN IMMEDIATE مع isolation_level=None؟ للتحكم اليدوي الصريح ببداية المعاملة ونهايتها ومنع تعارض الكتابة المتزامنة.
  8. كيف تمنع حقن SQL (SQL Injection)؟ باستخدام المعاملات (?) في جميع استعلامات execute(sql, params) وعدم دمج نصوص المستخدم في الاستعلام.
  9. ما فائدة الفهارس (CREATE INDEX) في الجداول؟ لتسريع البحث والاستعلام عن أسماء الأدوية وتواريخ الصلاحية والفواتير عند كبر حجم البيانات.
  10. ما وظيفة جدول stock_adjustments؟ سجل تدقيق غير قابل للتجاوز يحفظ كل حركة تغيير في المخزون مع السبب والوقت والمرجع.

رابعاً: أسئلة منطق الصيدلية (POS & Expiry & Profit)

  1. ماذا يحدث عندما يحاول الكاشير بيع دواء منتهي الصلاحية؟ تمنعه دالة validate_medicine_for_cart في الواجهة، كما تمنعه create_sale داخل معاملة قاعدة البيانات وترفع BusinessRuleError.
  2. هل يُسمح ببيع الدواء في يوم انتهاء صلاحيته نفسه؟ لا؛ وفق دالة is_expired الشرط هو exp <= ref، أي يُحظر من يوم الانتهاء فصاعداً حرصاً على سلامة المريض.
  3. كيف يحسب نظام POS الإجمالي والخصم والضريبة؟ الإجمالي الفرعي = مجموع (السعر × الكمية)، ثم يُخصم الخصم النقدي، ثم تُحسب الضريبة على المبلغ الخاضع بعد الخصم، ثم يُجمعان للحصول على الإجمالي النهائي.
  4. كيف يحسب النظام صافي الربح (Net Profit)؟ يحسب الفرق بين سعر البيع وسعر التكلفة (unit_price - cost_price) لكل وحدة مباعة، ثم يطرح قيمة الخصم الممنوح على الفاتورة.
  5. كيف يدعم النظام مبدأ FEFO (First Expired, First Out)؟ عبر ترتيب الاستعلامات حسب expiry_date ASC وعرض نافذة تنبيه قابلة للضبط (15/30/60/90 يوماً) في صفحة التنبيهات.

خامساً: أسئلة Streamlit ونسخة الويب والتوطين

  1. ماذا يحدث عند حدوث Rerun في Streamlit؟ يعيد Streamlit تنفيذ ملف web_app/app.py من السطر الأول للأسفل لتحديث الواجهة بناءً على مدخلات المستخدم الجديدة.
  2. كيف تحافظ على سلة المشتريات واللغة أثناء الـ Rerun؟ باستخدام st.session_state عبر WebSessionController لتخزين السلة واللغة المختارة ومفتاح الصفحة المستقر.
  3. كيف منعت تكرار الفواتير عند إعادة التشغيل السريع في POS؟ باستخدام رمز معاملة لمرة واحدة rxcare_pos_tx_token؛ بعد إتمام البيع يُسجل الرمز في rxcare_processed_tx_tokens وتُفرغ السلة ويُستبدل الرمز.
  4. لماذا احتجنا check_same_thread=False و RLock في نسخة الويب؟ لأن Streamlit يشغل الجلسات عبر خيوط متعددة، وRLock يمنع تداخل معاملات SQLite بين الخيوط.
  5. كيف حققت التبديل بين العربية (RTL) والإنجليزية (LTR) دون فقدان السلة؟ بفصل مفاتيح الصفحات (NAV_PAGE_KEYS) عن النصوص المترجمة في i18n.py وتطبيق CSS ديناميكي لـ direction: rtl/ltr.
  6. ما فائدة @st.cache_resource على get_web_app_container()؟ يضمن إنشاء اتصال قاعدة بيانات واحد ومشترك لعملية الخادم بدلاً من فتح اتصال جديد مع كل Rerun.
  7. كيف حللت مشكلة عرض الحروف العربية في رسوم Matplotlib؟ بإنشاء وحدة web_app/core/arabic_shape.py لتشكيل الحروف العربية بصيغة Presentation Forms-B وعكس الترتيب البصري لـ RTL مع بقاء الأرقام LTR.

سادساً: أسئلة الاختبارات والأمان والقيود والنشر

  1. ما الفرق بين اختبار الوحدة (Unit Test) واختبار التكامل (Integration Test)؟ اختبار الوحدة يفحص دالة صغيرة منفردة (مثل حساب المجموع)، أما التكامل فيفحص تفاعل الخدمة مع قاعدة البيانات الحقيقية (مثل create_sale + خصم المخزون + سجل التدقيق).
  2. ما أبرز قيود النسخة المنشورة حالياً على Streamlit Cloud؟ ملف SQLite المحلي قد يُعاد ضبطه عند إعادة تشغيل الحاوية السحابية، ولا يوجد تسجيل دخول متعدد المستخدمين بعد.
  3. كيف يمكنك ترقية النظام لاستخدام قاعدة بيانات سحابية دائمة مستقبلاً؟ بتنفيذ فئة جديدة تطابق بروتوكول DatabaseBackend تتصل بـ PostgreSQL وربطها داخل create_database_backend() عند تمرير RXCARE_WEB_DB_URL.
  4. ما الفرق بين ملف data/pharmacy.db و data/pharmacy_web.db؟ الأول خاص بالنسخة المكتبية، والثاني معزول لنسخة الويب حتى لا تؤثر تجربة الويب على بيانات سطح المكتب.
  5. لماذا وضعنا .streamlit/config.toml في جذر المستودع وليس داخل web_app/؟ لأن Streamlit و Streamlit Community Cloud يقرآن ملف الإعدادات من جذر مجلد التشغيل فقط.
